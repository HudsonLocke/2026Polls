------------------------------------------------------------------------------
1. WHAT THIS IS
------------------------------------------------------------------------------

A compiled dataset of public opinion polls for the 2026 United States midterm
elections, covering U.S. Senate races, gubernatorial races, U.S. House races
(district-level), and the national congressional generic ballot. It includes
the final pre-election polls released in the days before 3 November 2026 and
the full earlier history each source carries, back to 2023 in places, so trend
lines can be rebuilt from scratch. Primary-election and runoff polling is
included and flagged, not dropped.

The data is stored in long format: one row per candidate per poll question. A
poll that asked two different matchups produces two question_ids; a matchup
with four named candidates produces four rows under one question_id.
poll_questions_2026.csv collapses that to one row per question if you want a
wide-ish view.

------------------------------------------------------------------------------
2. SOURCES, AND WHY THESE ONES
------------------------------------------------------------------------------

FiveThirtyEight was the standard bulk source for raw poll data through 2024.
It no longer exists: as of this compile, every URL under
projects.fivethirtyeight.com/polls/data/ (senate_polls.csv,
governor_polls.csv, house_polls.csv, generic_ballot_polls.csv) returns an HTTP
302 redirect chain that ends at abcnews.com/politics, serving HTML rather than
CSV. The GitHub mirror fivethirtyeight/data no longer carries a polls/
directory for this cycle either. RealClearPolitics / RealClearPolling and
270toWin both return HTTP 403 to non-browser clients and publish no bulk
export. Race to the WH publishes its poll list only through Infogram embeds
whose stored payload was last updated in March 2026 and contains no poll rows.
So the three sources below are what is actually obtainable in bulk right now.

  SOURCE 1 -- VoteHub Polls API  (primary bulk source)
  ------------------------------------------------------------
      Endpoint:  https://api.votehub.com/polls
      Format:    JSON array, one object per poll, nested 'answers' array
      Auth:      none; free, no API key
      Behaviour: returns the ENTIRE poll history on every call, all offices at
                 once. Query parameters such as ?type=senate are accepted but
                 ignored -- the response is byte-identical -- so the full file is
                 downloaded once and split locally on the poll_type field.
      License:   published as CC BY 4.0 by VoteHub.
      Covers:    poll_type values us-senator, governor, us-representative,
                 generic-ballot (also approval / favorability / primaries /
                 attorney-general / mayor / propositions, which were not used).
      Yield:     1,878 poll questions, 239 firms

  SOURCE 2 -- Wikipedia per-race polling tables  (broadest firm coverage)
  ------------------------------------------------------------
      Endpoints: https://en.wikipedia.org/w/api.php          (page discovery)
                 https://en.wikipedia.org/api/rest_v1/page/html/<title>
      Format:    Parsoid HTML, parsed with BeautifulSoup + lxml
      License:   text is CC BY-SA 4.0. Attribution required if redistributed.
      Pages:     160 candidate pages discovered, every page fetched
      Yield:     3,705 poll questions, 374 firms
      Why:       Wikipedia's race articles list campaign internals, state-level
                 university polls, and small partisan shops that national
                 aggregators skip, which is where most of the extra firm count
                 comes from. It is also the only bulk-reachable source with
                 primary and runoff polling at district level.

  SOURCE 3 -- Silver Bulletin generic ballot database
  ------------------------------------------------------------
      Endpoint:  Google Sheets CSV export linked from
                 https://www.natesilver.net/p/generic-ballot-average-2026-nate-
                 silver-bulletin-congress-polls
                 (docs.google.com/spreadsheets/d/e/2PACX-1vRsvXNCZ0ubJr8D_yNcU5
                 q6C0_HBa35K7oDK03KpO7Ca43UwdXaIdvVLWoXEmHHph0EREz5430Hm5yZ/pub
                 ?output=csv)
      Format:    CSV, one row per generic-ballot poll
      Yield:     690 generic-ballot questions, 79 firms
      Extra:     this source is the only one carrying house-effect-ADJUSTED
                 numbers (adjusted_dem / adjusted_rep / adjusted_net) alongside
                 the raw toplines, plus each poll's model weight and influence.
                 Those columns are preserved in
                 source_data/silver_bulletin_generic_ballot_with_adjusted.csv
                 because the combined files only carry raw toplines.

3. EXACTLY HOW IT WAS COLLECTED
------------------------------------------------------------------------------

  Step 0 -- Source probe
      curl -I over every candidate bulk endpoint to see what still responds with
      data rather than HTML or a 403. This is what established that the
      FiveThirtyEight CSVs are gone (see section 2).

  Step 1 -- VoteHub
      curl -L https://api.votehub.com/polls  ->  raw JSON saved verbatim.
      Split on poll_type. The race is identified by the free-text 'subject'
      field, which uses three shapes:
          '2026 Ohio'              -> state race, general election
          '2026 Texas Democratic'  -> state race, Democratic primary
          '2026 AK-01'             -> House district
          '2026'                   -> national generic ballot
      These were parsed into separate state / district / race_stage columns.

  Step 2 -- Wikipedia page discovery
      Four methods were unioned so no race was missed because of a title
      convention:
          action=query&list=allpages&apprefix=...   for the predictable titles
            ('2026 United States Senate election', '2026 United States House of
             Representatives election', 'Opinion polling for the 2026', ...)
          action=query&list=search&srsearch=intitle:...   for governor races,
            which are titled '2026 <State> gubernatorial election', and for
            'congressional district' special-election pages
          action=query&prop=links   on the four hub pages (2026 United States
            Senate elections / House of Representatives elections /
            gubernatorial elections / elections)
      The raw union was 260 pages. It was then filtered to U.S. federal and
      U.S. governor races only. Two classes of false positive had to be removed:
          - STATE legislatures. '2026 Alabama Senate election' and '2026 Alabama
            House of Representatives election' are the state legislature, not
            Congress. Only the 'United States Senate election in X' /
            'United States House of Representatives election(s) in X' forms are
            federal.
          - Foreign races. '2026 French Senate election', '2026 Bangkok
            gubernatorial election', Russian oblast governorships, Nigerian state
            governorships, Japanese prefectural governorships, Brazilian general
            elections, and the Spanish / New Zealand polling pages all match the
            same title patterns.
      Governor pages were additionally checked against an explicit list of the 50
      states, DC, and the five territories.
      Result: 160 pages, listed in source_data/wikipedia_pages_used.txt.

  Step 3 -- Wikipedia table parsing
      Each page was fetched from the REST HTML endpoint and every <table> walked.
      A table was treated as a polling table only if a header row within its
      first six rows was mostly <th>, matched /poll source|pollster|poll|source/,
      AND matched /date/. That rejects results tables, endorsement lists,
      fundraising tables, and race-rating tables.
      Mechanics that mattered:
          - rowspan / colspan. Wikipedia poll tables routinely rowspan the
            pollster and date cells across several matchup rows. Every table was
            expanded into a dense grid first, so a rowspanned pollster is carried
            down to each matchup row instead of being read as blank.
          - Column roles were assigned from the header text: pollster, date,
            sample size, margin of error, sponsor, undecided, other, lead. Any
            remaining non-empty, non-metadata header was treated as a candidate
            column and melted into rows.
          - <sup> elements were stripped and bracketed footnote markers removed
            before reading any cell, so '47%[a]' parses as 47.0 and
            'Emerson College[12]' as 'Emerson College'.
          - Date strings were parsed from six observed shapes, including
            'October 28-30, 2026', 'Oct 28 - Nov 1, 2026', '28-30 October 2026'
            and bare single dates, with the year inferred from the page title
            when the cell omitted it. A cross-month range whose end month is
            earlier than its start month is rolled to the following year.
          - The nearest preceding heading chain was recorded as wiki_section,
            which is what supplies race_stage (General / Democratic primary /
            Republican primary / Runoff / Special general) and, on multi-district
            state pages, the district number.
      Requests were rate-limited to roughly one per 1.1 seconds with a
      descriptive User-Agent and exponential backoff on HTTP 429/503, after an
      unthrottled first attempt was rate-limited. Every response was cached to
      disk so the run is reproducible without re-hitting the API.

  Step 4 -- Silver Bulletin
      The article HTML was fetched and scanned for data links; it embeds a
      published Google Sheets CSV export, which was downloaded directly.

  Step 5 -- Normalisation
      All three sources were mapped onto one schema (section 4). Specifically:
          - State names were normalised both ways, because VoteHub mixes postal
            codes ('AK', 'MI') and full names ('Alaska', 'Michigan') in the same
            field. Both state and state_po are populated.
          - Candidate party was taken from a trailing party suffix in the
            candidate label where one existed: (D) (R) (I) (L) (G) (C) (NP)
            (NPA) (WFP) (PSL) and others, plus 'Dem' / 'Rep' /
            'Generic Democrat' style labels. Minnesota's DFL and North
            Dakota's Democratic-NPL were mapped to D, since those are those
            states' Democratic parties.
          - Most sources do NOT label party at all -- VoteHub just gives bare
            candidate names, and Wikipedia omits the suffix inside primary
            tables. Party was therefore backfilled in three passes, each
            recorded in data_quality_flag so you can audit or discard it:
              1. party_inferred_from_name: a candidate who carries an explicit
                 party label on SOME row gets that party on rows where the
                 label is missing. Matched on a normalised name, scoped to the
                 same state and office first, then globally for full names.
              2. party_inferred_from_primary: in a Democratic or Republican
                 primary poll, every candidate is of that party.
              3. party_inferred_as_sole_opponent: in a general-election
                 question with exactly two named candidates, where one is a
                 known D or R and the other carries no party label ANYWHERE in
                 the dataset, the second is assigned the opposite major party.
                 This is the one inference that can be flatly wrong -- an
                 unlabelled independent or nonpartisan candidate gets assigned
                 D or R by it. It fired on a small number of rows; filter the
                 flag out if that matters to you.
          - Rows whose pollster cell parsed as a number, a percentage or a
            sample-size string, and rows whose candidate was a table artefact
            such as 'RCV round' in Alaska's ranked-choice tables, were dropped
            as parser misalignment rather than kept as data.
          - Pollster partisan lean: Wikipedia encodes it in the firm name
            ('Cygnal (R)', 'Impact Research (D)'). That suffix was moved out of
            the pollster name into pollster_partisan_lean so that 'Cygnal (R)'
            and 'Cygnal' are the same firm, and internal_poll was set TRUE for
            those rows. VoteHub and Silver Bulletin have their own partisan
            fields, which were used as-is.
          - dem_pct / rep_pct / margin_dem_minus_rep were computed per question
            from the first Democratic and first Republican candidate in that
            question, so two-way margins are directly usable.
          - days_to_election = 2026-11-03 minus the poll's end date. Negative
            values would mean post-election fieldwork; there are none.

  Step 6 -- Prediction-market odds
      Kalshi and Polymarket win probabilities were attached to every
      general-election poll, averaged over the poll's fieldwork window.
      Section 10 has the detail.

5. THINGS YOU NEED TO KNOW BEFORE USING THIS
------------------------------------------------------------------------------

DEDUPLICATION -- READ THIS BEFORE AVERAGING ANYTHING

SOURCES OVERLAP AND ARE NOT DEDUPLICATED. A poll carried by both VoteHub and
Wikipedia appears twice, once per source. This is deliberate: the two records
often disagree on sample size, population or rounding, and silently picking a
winner would hide that. 932 dedupe_key values appear under more than one
source. Any average computed over these files without deduplicating will
double-count.

THE WORK IS ALREADY DONE FOR YOU: deduped/ holds a merged, one-record-per-
question version of every file. Use it unless you specifically want to compare
what the sources disagreed about. Section 9 explains how the merge works and
what it can get wrong. The files at the top level stay un-deduplicated on
purpose, as the audit trail behind it.

If you would rather do it yourself, deduplicate on dedupe_key, which is
office|state_po|district|race_stage|normalised pollster|end_date. The pollster
normalisation lowercases, strips a partisan suffix, strips a leading 'The' and
strips punctuation, so 'The New York Times/Siena University' and 'New York
Times / Siena University' collapse to one firm. Simplest alternative: filter
to a single source and ignore the rest.

One nuance: a dedupe_key can legitimately cover several DIFFERENT questions,
because one poll often asks more than one matchup (a head-to-head, then the
same race with a third-party candidate added, then a primary). Those share
firm, race and date but are not duplicates of each other. If you want one
number per poll, group by dedupe_key and pick a question deliberately -- the
4,742 general-election questions collapse to roughly 2,674 firm-race-date
combinations.

FABRICATED POLLS ARE PRESENT AND FLAGGED, NOT DELETED

2026 had a run of firms publishing invented numbers. Wedgewood Polls admitted
on 20 October 2026 that most of its results were made up, including its
battleground surveys of Texas, Ohio, Michigan, Kansas and Maine; it called the
exercise an experiment in how easily fake polling spreads. The New York Times
pulled roughly 15 of its surveys and Decision Desk HQ pulled 17 from its
averages. Earlier, in August 2026, Median Strategies admitted its Los Angeles
mayoral, Wisconsin and Nevada polls were fabricated and shut down.
FiftyPlusOne has also suspended a separate firm over alleged falsified data in
a Florida Republican gubernatorial primary survey.

Wedgewood Polls is still carried by VoteHub and so appears here: 11 poll
questions, 23 candidate rows. Those rows were NOT deleted, because a silent
deletion is worse than a labelled one -- you should be able to see what the
aggregators were carrying. Every one is tagged 'pollster_admitted_fabrication'
in data_quality_flag. Exclude that flag before computing anything. Median
Strategies produced no rows in these sources, so there is nothing to filter
for it.

That list is only the firms caught before this compile. Treat any unfamiliar
pollster with no track record, no named principal and no published methodology
as unverified -- that was the common signature in all three 2026 cases.

PRIMARY AND GENERAL POLLING ARE MIXED IN THE SAME FILES, separated by
race_stage. VoteHub in particular does not flag primaries in a dedicated field
-- the only signal is the 'Democratic' / 'Republican' suffix on its subject
string, which it uses inconsistently, so some primary polling may be labelled
'General'. Wikipedia's section headings are the more reliable stage signal.
Filter race_stage == 'General' for general-election work.

HOUSE COVERAGE IS SPARSE AND NON-RANDOM, in the data and in reality. Only
competitive districts get polled, and most of what exists is campaign
internals released because they were favourable. Treat district-level numbers,
and any average of them, with much more suspicion than Senate or governor
numbers.

MARGIN OF ERROR IS MOSTLY EMPTY for VoteHub and Silver Bulletin rows, because
neither source carries it. It is populated for most Wikipedia rows. Do not
read a blank as 'no sampling error'.

THE 'FINAL' POLLS ARE THE LAST ONES RELEASED, not a complete census of final
polls. Firms that fielded through 2 November but released after the election,
or never released, are absent. Late polling is also the most crowded with
partisan releases.

WIKIPEDIA ROWS ARE MACHINE-PARSED and carry the error rate of that. The parser
was checked by hand against several race pages, but a header it did not
recognise becomes a candidate column, and an unusual date string can fail to
parse. wiki_page and wiki_section are on every row so any value can be traced
back to the table it came from. Wikipedia itself is also a secondary source
that anyone can edit.

SOME CANDIDATE COLUMNS ARE NOT PEOPLE. 'Generic Democrat', 'Generic
Republican', 'Someone else' and similar appear as candidate values where a
poll asked a generic matchup. They are kept, with blank or inferred party.

PARTY LABELS ARE PARTLY INFERRED, and dem_pct / rep_pct / margin_dem_minus_rep
are derived from them. Every inferred row says so in data_quality_flag (see
section 3, step 5). The candidate and pct columns are always as the source
gave them; the party and margin columns are the ones to distrust.

270 general-election questions carry no D-R margin, because no candidate in
them could be identified as a Democrat or a Republican -- typically a poll of
a jungle primary, an all-independent ballot test, or a matchup listing only
one named candidate. The candidate-level rows are still there; only the
convenience columns are blank.

9. THE DEDUPED FILES -- HOW THE MERGE WORKS
------------------------------------------------------------------------------

      15,764 rows / 6,273 questions   ->   13,752 rows / 5,314 questions
      959 duplicate questions removed. 484 firms remain (of 490).

The merge is NOT a pick-a-winner. Measured across the whole dataset, Wikipedia
carries a margin of error on 87% of its questions and an undecided figure on
91%, but no poll URL and no sponsor at all. VoteHub and Silver Bulletin carry
a URL on 100% and a sponsor on roughly half, but never a margin of error or an
undecided figure. The sources are complementary, so discarding either one
throws away columns the other does not have.

So duplicate records are merged instead. One record supplies the candidate
names and percentages; the others fill in whichever of sample_size,
population, margin_of_error, url, sponsors, undecided_pct and other_pct it was
missing. On the 959 questions that more than one source carried, the result
has a margin of error on 90% AND a URL on 99% -- a combination neither source
could produce alone.

  How two records are judged to be the same question
  ------------------------------------------------------------
      Candidates are reduced to surnames, lowercased, with suffixes and party
      tags stripped; 'Other', 'Undecided', 'Generic Democrat' and similar non-
      people are ignored. For the generic ballot, which has no candidates, the
      comparison is on party instead, because Silver Bulletin writes
      'Democratic candidate' where VoteHub writes 'Dem'. Within one
      dedupe_key, records from DIFFERENT sources are then matched:

        EXACT   identical surname sets. Always merged.
        PARTIAL one set is a strict subset of the other (a source that left out
                the minor candidates), at least two surnames are shared, and the
                Jaccard overlap exceeds 0.6. Merged and labelled.
        neither -> kept as separate questions.

      Records from the SAME source are never merged into each other. When a
      source lists two matchups for one poll -- a head-to-head, then the same
      race with a third-party candidate added -- those are two real questions,
      and collapsing them would delete a ballot test the pollster actually
      asked.

      The partial rule needs all three of its conditions. An earlier version
      accepted a Jaccard overlap of 0.5 with no subset or shared-count test,
      and it merged things that are not the same question: Alaska's four-way
      first-past-the-post gubernatorial question with a two-way from the same
      poll, a 'Hyde-Smith vs Generic Opponent' test with a real 'Hyde-Smith vs
      Colom' matchup, and a Hochul-vs-Blakeman matchup with a Hochul-only row.
      Those three are kept apart in the files you have.

  New columns in deduped/
  ------------------------------------------------------------
      sources               every source that carried this question
      source               the one whose candidate names and percentages were kept
      n_source_records      how many source records went into this row (1 = unique)
      match_rule            unique | exact | partial
      source_pct_max_delta  largest percentage-point gap between the sources on any
                            candidate they both listed; blank when only one source
                            had it

  Do the sources actually agree?
  ------------------------------------------------------------
      785 of 959 merged questions agree to the decimal.
      31 differ by more than one point, 7 by more than five.

      Those are kept, flagged 'source_pct_disagreement', because they are real
      conflicts in the published record rather than merge errors. Checked by
      hand, the worst of them follow one pattern: the two sources agree
      exactly on the Democrat and the Republican and disagree about a minor
      candidate. In Montana's 2nd district, both have Downing on 29 and Miller
      on 18, while Wikipedia lists Eisenhauer on 15 and VoteHub lists him on 2
      with an extra candidate on 15 -- a transcription slip on one side or the
      other. The merged row keeps one version; the top-level files keep both,
      so you can see what was dropped.

      What the merge cannot fix: if two sources transcribed the same poll with
      different numbers, one of them is wrong and this dataset does not know
      which. If that matters for a specific poll, follow the url column to the
      pollster's own release.

10. PREDICTION-MARKET ODDS
------------------------------------------------------------------------------

Every general-election poll carries the Kalshi and Polymarket probability that
each party wins that race, averaged over the days the poll was actually in the
field (start_date to end_date inclusive). So the odds sit beside the poll as
they stood while it was being conducted, not as they stood on election day.

      general-election questions          4,742
      with Kalshi odds                    2,573  (54%)
      with Polymarket odds                3,500  (74%)
      with at least one of the two        3,917  (83%)

  Sources
  ------------------------------------------------------------
      Kalshi      https://api.elections.kalshi.com/trade-api/v2
                    /series?limit=2              (returns all ~15,900 series)
                    /markets?series_ticker=<S>   (the contracts in a series)
                    /series/<S>/markets/<T>/candlesticks
                      ?start_ts=&end_ts=&period_interval=1440
                  Public, no API key. The candlestick span is capped per
                  request, so history was walked in 180-day chunks. Daily mean
                  price was used (mean_dollars), falling back to the close.
                  NOTE: api.elections.kalshi.com is the open host;
                  trading-api.kalshi.com returns 401 without credentials.

      Polymarket  https://gamma-api.polymarket.com
                    /public-search?q=<race>      (find the event)
                    /events?slug=<slug>          (its candidate contracts)
                  https://clob.polymarket.com
                    /prices-history?market=<clobTokenId>&interval=max&fidelity=1440
                  Public, no API key. The startTs/endTs form of prices-history
                  returns 400 ('interval is too long') for spans of this length
                  at daily fidelity, so interval=max was used and the series
                  filtered locally. Intraday points on the same day were averaged.

  Matching a market to a race
  ------------------------------------------------------------
      Kalshi series follow per-race ticker patterns -- SENATE<ST>,
      SENATEPARTY<ST>, GOVPARTY<ST>, HOUSE<ST><DD>, each optionally KX-
      prefixed, plus a trailing S for special elections (SENATEOHS,
      SENATEFLS). Inside a series, the contract ticker ends -D or -R, which
      gives the party directly.

      Deciding WHICH ELECTION a contract belongs to needed two signals,
      because neither works alone. The ticker's cycle tag is sometimes the
      term year rather than the election year -- New Hampshire's governor
      contracts are GOVPARTYNH-28-D/R but closed 2026-11-04. And some 2026
      contracts have a close_time a year past the election (SENATEAK-26 closes
      2027-11-03). Filtering on the tag alone silently dropped Ohio and
      Florida; filtering on close_time alone silently dropped Alaska and
      Mississippi. A contract is therefore accepted when its tag matches the
      cycle OR it closes in the election window, and rejected whenever its tag
      names a later cycle.

      Polymarket has no race-ticker scheme, so each race was searched by name
      and the returned events were validated before use: the slug or title
      must contain 'winner' and the state, must match the office, must NOT be
      a margin, turnout, primary, nominee, runoff or combo market, and must
      carry contracts whose titles end in (D) or (R).

      Market coverage by office (races with at least one platform):
        Senate           Kalshi  29 races   Polymarket  27 races
        Governor         Kalshi  32 races   Polymarket  34 races
        House            Kalshi  14 races   Polymarket  50 races
        Generic ballot   Kalshi   0 races   Polymarket   1 races

  Do the two platforms agree?
  ------------------------------------------------------------
      On the 2,156 questions covered by both, the two platforms'
      Democratic win probability differs by a median of 0.012 and a mean
      of 0.018. They were built from completely separate APIs with
      separate race-matching logic, so that agreement is a useful check that
      the matching and the window averaging are not scrambled.

  WHAT TO WATCH OUT FOR
  ------------------------------------------------------------
      THESE ODDS ARE NOT INDEPENDENT OF THE POLLS. Prediction markets move
      partly in response to published polling, including the polls in this
      dataset. Treating the market number as outside confirmation of the poll
      next to it is circular. The honest use is the reverse: see what the
      market thought while a poll was in the field.

      KALSHI'S TWO LEGS DO NOT ALWAYS SUM TO 1. Each party is a separate
      binary contract, so a thin market can price both sides high at once:
      FL-13 sat at D 0.78 and R 0.74 simultaneously. Of 5,839 rows with both
      legs, 292 sum outside 0.90-1.10, and market_note records the sum
      whenever it strays that far. Use kalshi_dem_prob_norm, which divides by
      the total, for anything quantitative. Polymarket's contracts are
      mutually exclusive within an event and behave better.

      THE GENERIC BALLOT IS MATCHED TO A DIFFERENT QUANTITY. There is no
      market on the national House popular vote share, so generic-ballot polls
      carry the probability that Democrats WIN THE HOUSE (Polymarket's which-
      party-will-win-the-house-in-2026). Vote share and seat control are not
      the same thing, and the gap between them is the whole subject of
      redistricting. Those rows say so in market_note. An earlier version
      summed the House-control and Senate-control contracts together and
      produced a Democratic probability of 1.64; only the House market is used
      now.

      NO ODDS BEFORE THE MARKET EXISTED. Kalshi history in this dataset starts
      2024-12-03 and Polymarket's 2025-06-11. Polls fielded earlier get blanks
      and a 'had_no_prices_in_window' note. Primary polls get no odds at all
      -- these are general-election win markets -- flagged
      'not_a_general_election_question'.

      A FEW PARTY PROBABILITIES ARE SUMS OVER A FIELD. Where an event listed
      several candidates of one party (New Jersey's 2025 governor event
      carried six Democrats and five Republicans), the party probability is
      the sum of its candidates' mutually exclusive contracts. market_note
      says so with 'party_prob_is_sum_of_N_candidates'.

      NO LIQUIDITY FILTER WAS APPLIED. A probability from a market with almost
      no volume is in here on the same footing as one from a heavily traded
      race. District-level markets are the thin ones. kalshi_days_in_window
      and polymarket_days_in_window show how many days actually had a price,
      which is the best liquidity proxy available here.

      WINDOW MECHANICS. The average covers start_date to end_date inclusive;
      where a source gave no start_date, end_date alone is used. Windows
      longer than 120 days (a handful of malformed source dates) are clamped
      to the last 120 days. A day with no trade contributes nothing rather
      than being interpolated.
